# Smart Agriculture Backend and Frontend Project Audit

**Audit phase:** Phase 1 — project audit and architecture review  
**Audit date:** 2026-11-22  
**Scope:** Read-only inspection of the existing backend, frontend, database wiring, disease model assets, tests, and configuration. No application source was changed for this audit.

## Executive summary

The project is a modular FastAPI application with a React/Vite frontend, MongoDB repositories, JWT role checks, adapters for weather/SMS/payments/escrow, and a local MobileNetV2 disease classifier. FastAPI OpenAPI contains **75 API method/path operations**. The checked-in backend test suite passes **59 tests**. The model file and 11-label JSON are present in this local checkout and the model loads with input `(None, 224, 224, 3)` and output `(None, 11)`; an RGB synthetic JPEG completed inference. This does not establish accuracy on Kenyan field photos.

The implementation is a useful marketplace/payment baseline, but it does not yet implement the larger agricultural product scope in the supplied specification: disease knowledge and treatment recommendations, disease follow-up/treatment records, crop calendars, fertilizer advice, a pest knowledge base, a source-traceable knowledge centre, officer case assignment/review, or a verified market-price ingestion source. These should be built in later phases using verifiable sources and explicit approval workflows, not filled with fabricated data.

## Database and configuration observations

- `app/core/config.py` loads a backend-root `.env` file using Pydantic Settings. `.env` is ignored by Git and is not tracked in this working tree. No credential value was included in this report.
- `app/core/database.py` creates a shared PyMongo client lazily and uses `admin.command('ping')` for readiness. This audit did not connect to or mutate the configured MongoDB database.
- Repositories create indexes in repository constructors. Existing indexes cover user/profile uniqueness, owner/date lookups, product browse filters, payment idempotency/provider references, unique escrow/order, notification idempotency, and ledger idempotency/order history. Verify Atlas user permissions include index creation or provision indexes separately if production credentials are deliberately restricted.
- ObjectIds are used in Mongo references and converted by repository public-document helpers. UTC timestamps are present in public schemas. Audit of all repository response shapes and ownership paths is part of stabilization/regression work, not certified by this architecture inventory.
- `.env.example` contains names and placeholders. Keep actual `.env` and production credentials out of Git and Postman exports.

## Phase 4: PCPB evidence review workflow

A new `pesticide_records` collection stores PCPB registration evidence and its linked approved label. Admins and agricultural officers may submit evidence records as `PENDING_REVIEW`; only ADMIN can approve or reject. Approval requires the administrator to attest that both the current official PCPB registration and approved label were checked. The reviewer, decision, note, check date, and timestamp are appended to `review_events`. Farmers can list only `APPROVED` records; the API does not generate a product application rate or recommend pesticide use.

New APIs:

| Method | Endpoint | Access |
|---|---|---|
| POST | `/pesticide-records` | ADMIN or AGRICULTURAL_OFFICER; create pending evidence only |
| GET | `/pesticide-records` | ADMIN or AGRICULTURAL_OFFICER; paginated evidence queue, optional review status |
| PATCH | `/pesticide-records/{record_id}/review` | ADMIN; append approval/rejection audit event; pending records only |
| GET | `/pesticide-records/approved` | FARMER; list approved label records, optional crop-name filter |

The official registration source used as the system's evidence boundary is the PCPB [registered crop products register](https://www.pcpb.go.ke/crops/) and the corresponding official approved label linked there. No real product records were preloaded because this implementation has not manually verified a complete current set. The Postman requests in **Pesticide Evidence** use placeholders; replace them only with data checked against the official source before sending.

Phase 4 verification: full suite **67 passed, 0 failed, 0 skipped**; compileall succeeded; OpenAPI now reports **81 operations**. Tests use an in-memory pesticide repository and verify role restrictions, pending-only visibility, approval attestation, audit events, and duplicate review protection. They do not prove live Mongo index creation or any product's current registration.

## Phase 5: disease history and farmer monitoring

Added idempotent farmer activity logs, follow-up image screening, monitoring retrieval, farmer case resolution, officer review requests, an officer/admin review queue, and append-only officer notes. Follow-up images are screened through the existing model and only their hash and metadata are stored. Comparing follow-up and initial model labels is explicitly described as model-output comparison, not evidence of disease progression or recovery. Chemical treatment history requires an administrator-approved PCPB record matching the detected crop and disease; the API records the farmer's action and does not prescribe it. There are no invented treatment intervals.

| POST | `/disease-detection/{report_id}/followups` | Owning FARMER |

Uploading a follow-up requires deployed model assets and returns 503 otherwise.

## Phase 6: weather freshness and provider boundary

The existing OpenWeatherMap current + five-day/three-hour forecast adapter remains the provider boundary. It now caches successful forecasts in process memory per rounded coordinate and API-key hash (never logged) for `WEATHER_CACHE_TTL_SECONDS` (default 300, range 0-3600). Responses expose `cache_hit` and `cache_valid_until`. Cache TTL 0 disables it. The bounded cache is per process, is not a cross-worker rate limiter, and no live weather request was made in this implementation session. Weather tests mock provider responses and verify success caching, no-cache mode, missing-key behavior, and role restrictions.

## Phase 7: crop-stage calendar and soil education

Added `GET /crop-planning/crops/{crop_id}/calendar`, an owner-checked, source-linked stage checklist for maize, tomato, and potato, plus `POST /crop-planning/soil-guidance`, which stores a general soil-test-first advisory in the existing `advisories` collection. The calendar does not infer local planting dates or fixed task intervals. Soil guidance does not calculate nutrient quantities, interpret lab results, or recommend a fertilizer product. Both APIs return 404 for unavailable crop/farm records; calendar 404 also covers crops without reviewed content. Manual Postman requests added under **Crop Planning**. Content references KALRO and Kenya MoALD sources documented in README.

## Phase 8: pest knowledge

Added public `GET /pest-knowledge` (optional crop filter) and `GET /pest-knowledge/{slug}` with source-backed educational content for fall armyworm (maize) and tomato whitefly. It explicitly does not identify pests from images and contains no chemical recommendation. Current entry sources and the KALRO/FAO basis are linked in README and API response. New **Pest Knowledge** Postman folder included. Additional pests remain unavailable until reviewed information is sourced.
